3.0. [FAIT - QuickJS choisi sur les mesures New 3DS] Etude de faisabilite :
 - Compiler QuickJS ET un moteur plus leger (MuJS ou Duktape) pour la 3DS.
 Mesurer : taille du binaire, RAM au demarrage, temps d'un script de test
 (boucle de 100 000 iterations + manipulation de chaines).
 - Choisir le moteur sur ces mesures. Si QuickJS depasse le budget memoire
 (plus de 4 Mo de tas), prendre le moteur le plus leger : ES5 suffit pour
 la v0.4.
 - Realiste : les gros sites (frameworks) ne tourneront pas. Cible = petits
 scripts de formulaires, menus, compteurs, pages simples.
 - Sondes compilees : tests/jsbench/build/quickjs.3dsx et mujs.3dsx.
   Dernieres tailles 3DSX (sonde + moteur + libctru) : QuickJS 985 940 octets ;
   MuJS 444 236 octets. Le dump crash_dump_00000019.dmp correspond a MuJS
   (PC symbolise dans js_regcompx, cadre local d'environ 33 Kio). La sonde
   reserve maintenant 1 Mio de pile native comme le navigateur; le dump
   crash_dump_00000019.dmp a permis de corriger son plantage au demarrage.
   Mesures New 3DS : MuJS tas 154 419 octets a l'initialisation et 174 620
   apres le script, init 6 ms / script 1 900 ms, script_ok=1. QuickJS tas
   145 788 octets a l'initialisation et 146 556 apres le script, init 8 ms /
   script 333 ms, script_ok=1. QuickJS est retenu : il utilise moins de tas
   mesure et execute le script environ 5,7 fois plus vite; sa sonde est plus
   grande de 541 704 octets (985 940 contre 444 236). L'ancienne mesure
   QuickJS a 360 octets etait incomplete car newlib n'a pas
   malloc_usable_size; la sonde utilise maintenant un allocateur mesure
   avec limite stricte de 4 Mio. Les mesures systeme osGetMemRegionFree()
   a zero sont invalidees. L'utilisateur a explicitement autorise le passage
   a l'etape 3 malgre les validations console restantes de l'etape 2.

3.1. [CODE FAIT - VALIDATION NEW 3DS REQUISE] Integration du moteur JS choisi :
 - Limite stricte du tas JS : 2 a 4 Mo (JS_SetMemoryLimit pour QuickJS).
 - Limite de pile JS : 64 a 128 Ko (JS_SetMaxStackSize).
 - Un contexte par page ; liberer le contexte au changement de page.
 - Ajouter l'option de reglage enableJS (par defaut : DESACTIVE en v0.4).
 - QuickJS compile dans l'application avec un allocateur newlib mesure,
   tas limite a 4 Mio, pile JS limitee a 96 Kio; contextes ouverts par page
   si JavaScript est active, liberes lors de navigation/fermeture d'onglet.
   Le reglage est persistant et reste desactive par defaut. Build New 3DS
   passe avec 119 avertissements (niveau precedent); tests PC passes sans
   echec. Test console de cette integration a effectuer avant 3.2 : activer
   puis desactiver JavaScript, naviguer et fermer un onglet sans plantage.

3.2. Securite anti-freeze (watchdog) :
 - JS_SetInterruptHandler (ou equivalent) : si un script depasse 50 a 100 ms,
 l'execution est interrompue. Budget total par page : 300 ms.
 - Executer les scripts APRES le premier affichage de la page, jamais avant.
 - Pas de setTimeout/setInterval en v0.4, sauf un seul setTimeout borne
 (minimum 100 ms, maximum 5 appels par page).

3.3. Conservation des scripts dans le DOM (changement du parseur) :
 - Actuellement le contenu de <script> est jete (parser.cpp, ST_RAW). Pour
 l'etape 3, conserver le texte des scripts INLINE de moins de 32 Ko.
 - Scripts externes (src=...) : ignores en v0.4 (le chargement doit etre
 asynchrone, voir 2.1) ; prevoir 1 ou 2 scripts externes de moins de 64 Ko
 pour v0.5.

3.4. Bindings DOM minimaux :
 - document.getElementById(), querySelector (id et classe simples seulement).
 - element.innerText / textContent, element.style.display / color.
 - input.value (lecture/ecriture), form.submit().
 - onclick="..." et addEventListener('click', ...).
 - location.href = "...", alert("...") -> petite boite de dialogue sur
 l'ecran du bas (nouveau mode UiMode::Dialog avec bouton OK).
 - Les noeuds JS portent l'INDEX du noeud DOM ; ne jamais supprimer un
 noeud du vecteur (le marquer comme supprime) pour garder les index stables.
 - Apres une modification du DOM : poser un drapeau "dirty" et refaire la mise
 en page une seule fois par frame (throttle). Le PageRenderer devra alors
 recevoir forceRedraw() ET renvoyer la texture (voir 1.6.2).

3.5. Tests JS :
 - 5 pages de test : alerte, calcul dans un champ, afficher/masquer un bloc,
 boucle infinie (le watchdog doit couper), fuite memoire (limite du tas
 atteinte sans crash).
